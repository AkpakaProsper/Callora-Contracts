# Contract Error Codes

Stable, semantic `u32` error codes used by the Callora smart contracts.
These numeric discriminants are part of each contract's public interface and
must not be reassigned once released.

> This file is generated by `scripts/gen_error_codes.py`. Do not edit it
> by hand; run the script and commit the result. CI runs the script with
> `--check` and fails if this document diverges from the enums.

## Stability rules

- Preserve every existing numeric code for its current semantic meaning.
- Add new variants only with new, previously unused codes in that contract.
- Do not reuse a removed code for a different error.
- Codes marked **reserved** are not currently emitted by any variant.
- `cargo test --workspace err_stab` enforces code stability and duplicate-code checks.

## Admin

| Code | Variant | Contract | Meaning |
|------|---------|----------|---------|
| 1 | `NotInitialized` | Admin | Admin contract has not been initialized yet (code 1). |
| 2 | `Unauthorized` | Admin | Caller is not authorized for the requested operation (code 2). |
| 3 | `InvalidLimit` | Admin | One or more per-account caps exceeds [`crate::limits::MAX_CAP`] or is otherwise invalid (code 3). |
| 4 | `BetsAtCap` | Admin | Account's open bet count is already at the configured cap (code 4).  Returned by [`crate::limits::consume_bet`] when an increment would push the account's bet counter above `max_bets`. |
| 5 | `PositionsAtCap` | Admin | Account's open position count is already at the configured cap (code 5).  Returned by [`crate::limits::consume_position`] when an increment would push the account's position counter above `max_positions`. |
| 6 | `SubscriptionsAtCap` | Admin | Account's active subscription count is already at the configured cap (code 6).  Returned by [`crate::limits::consume_subscription`] when an increment would push the account's subscription counter above `max_subscriptions`. |
| 7 | `CounterUnderflow` | Admin | `release_*` was called when the corresponding counter was already zero (code 7). |
| 8 | `Overflow` | Admin | `checked_add` overflow detected on a counter increment (code 8).  Returned in the (effectively unreachable) case that the per-account counter arithmetic saturates `u32::MAX` — surfaces a stable error rather than panicking so callers can handle the edge case gracefully. |

| Code | Variant | Contract | Meaning |
|------|---------|----------|---------|
| 1 | `NotInitialized` | Batch Claim | Contract has not been initialized yet (code 1). |
| 2 | `AlreadyInitialized` | Batch Claim | Contract has already been initialized (code 2). |
| 3 | `Unauthorized` | Batch Claim | Caller is not the admin (code 3). |

| 5 | `AlreadySettled` | Batch Claim | Claim has already been collected (code 5). |
| 6 | `InvalidAmount` | Batch Claim | Claim amount must be > 0 (code 6). |
| 7 | `Overflow` | Batch Claim | Arithmetic overflow in pending-amount accumulation (code 7). |
| 8 | `ClaimIdAlreadyUsed` | Batch Claim | The claim identifier has already been consumed or cancelled; replay rejected (code 8).  Cancelled claims leave a tombstone (`ClaimConsumed(id) = true`) so the id can never be reissued to the same or any other claimant. |
| 9 | `ClaimIdMismatch` | Batch Claim | The provided claim_id does not match the stored record (code 9). |
| 10 | `InvalidClaimId` | Batch Claim | The claim identifier is malformed (code 10).  Issue #1044: the all-zero identifier is rejected because it is what an uninitialised buffer, a defaulted struct field, or a truncated encoding produces. Accepting it would let two unrelated bugs collide on the same "unique" id. |
| 11 | `BatchTooLarge` | Batch Claim | The batch exceeds [`crate::MAX_PENDING_AMOUNTS`] entries (code 11).  Issue #1044: bounds the work a single `batch_claim` invocation can do, so an oversized batch fails closed and cheaply instead of running the ledger out of resources part-way through a settlement. |
| 12 | `BatchEmpty` | Batch Claim | The batch input is empty (code 12).  Issue #1044: an empty batch is rejected rather than silently succeeding, so client bugs surface as errors instead of wasting fees on a no-op settlement. |

## Migrate

| Code | Variant | Contract | Meaning |
|------|---------|----------|---------|
| 1 | `NotInitialized` | Migrate | The contract has not been initialized.  Call [`EmergencyMigration::init`] before any other entrypoint. |
| 2 | `AlreadyInitialized` | Migrate | Initialization was attempted more than once.  The contract stores its admin during `init`; a second call is rejected. |
| 3 | `Unauthorized` | Migrate | The caller is not the configured administrator.  All state-changing entrypoints check that the caller equals the admin address stored at initialization time. |
| 4 | `LegacyStateMissing` | Migrate | No legacy state was found in storage.  The migration contract expects the previous deployment to have written a [`LegacyData`] record under [`StorageKey::Legacy`] before `migrate` is called. This error is returned when that key is absent. |
| 5 | `InvalidLegacyBalance` | Migrate | The legacy balance is negative, which indicates data corruption or an invalid deployment state.  Migration is refused when `legacy.balance < 0` to prevent introducing a negative balance into the new storage layout. |
| 6 | `VersionMismatch` | Migrate | The supplied `expected_version` does not match the stored version.  This guard prevents running a migration step out of order and serves as a concurrency safety check: if two operators race to call `migrate`, only the first succeeds. |
| 7 | `InvalidTargetVersion` | Migrate | The requested `target_version` is not exactly `expected_version + 1`.  The contract enforces a strictly-monotonic, no-skip version sequence. Skipping versions or providing a target equal to or below the current version raises this error. |
| 8 | `AlreadyMigrated` | Migrate | Migration has already been performed for the requested state.  Once the reshaped [`CurrentData`] record is written to storage, further `migrate` calls are rejected to ensure the reshape runs at most once. |
| 9 | `UpgradeNotAuthorized` | Migrate | No upgrade has been authorized for the requested version.  [`EmergencyMigration::authorize_upgrade`] must be called first with the correct `target_version` and `wasm_hash` before a deployment tool may proceed with the platform-level WASM swap. |
| 10 | `VersionOverflow` | Migrate | The migration version counter would overflow `u32::MAX`.  This is a defensive overflow guard on the `checked_add(1)` that advances the version. In practice, version numbers should never approach `u32::MAX`. |
| 11 | `InvalidInitialVersion` | Migrate | The `initial_version` supplied to `init` is unreasonably large.  Values greater than `u32::MAX - 1024` are rejected to reserve headroom for version increments and to guard against accidental very-large initial versions that would immediately overflow during migration. |
| 12 | `WasmHashZero` | Migrate | The supplied WASM hash is all zero bytes.  An all-zero hash is almost certainly a programming mistake (e.g. a zero-initialized buffer). Rejecting it early prevents accidentally authorizing an upgrade to an invalid WASM artifact. |
| 13 | `MigrationDataCorrupted` | Migrate | The stored current data fails internal consistency checks.  Raised when a post-migration view finds that `current.reserved < 0` or that `current.balance` differs from what was recorded at migration time — indicating unexpected direct-storage tampering. |
